# 面部混合语义调查（authored-curves 那一半）

调查目标：`authored-curves.json` 里那批曲线到底能不能施加，以及施加规则是什么。

调查日期：2026-11-08
范围：`NPC_00401`（参考）、`NPC_01101`（路易斯）、`NPC_06201`（伊里斯）

---

## 结论速览

| 问题 | 结论 |
|---|---|
| 这批曲线是什么 | 原版 `DataConfig/FacialAnimationData/TestData_1220003221_<npc>.uasset`，一段 8.725 s / 261 帧的**纯曲线**面部表演序列（无骨骼轨道） |
| 曲线值是什么 | **归一化权重**，不是弧度也不是米。全部落在 [-1, 1] |
| 曲线名是什么 | `<骨名>_<轴>_<通道>`，指向该角色 rig 里**真实存在**的骨骼与通道 |
| 施加规则 | 曲线值 = 权重；方向与幅度来自**同名 PoseAsset pose**（有 PoseAsset 时）或**标准表情动作**（无 PoseAsset 时） |
| 符号规则 | 每组 `X` / `X_Neg` 精确互逆（数值已验），`LipTogether` 是唯一例外 |
| 映射表在哪 | `DataConfig/FacialConfig/FacialSubModelConfig_NPC_<npc>.uasset` |
| 之前为什么没找到 | 这批资产不在角色的 `Animation/` 目录下，而在 `NewRoco/DataConfig/` 下，之前只按角色目录扫描过 |

## 1. 曲线值的量级 = 权重

伊里斯 113 条曲线，全部通道统计：

| 通道 | 条数 | max&#124;value&#124; |
|---|---|---|
| expression（LipTogether / EyeBlink / BrowUp / BrowDown） | 6 | 1.000 |
| position | 36 | 1.000 |
| rotation | 56 | 1.000 |
| scale | 15 | 1.000 |

每组 `X` / `X_Neg` 的曲线配对是**精确镜像**：正通道 ∈ [0, 1]，负通道 ∈ [-1, 0]，逐关键帧 `v_pos + v_neg = 0`（误差 < 1e-6）。

- 路易斯：80 组符号配对中 **79 组精确镜像**
- 伊里斯：51 组中 **50 组精确镜像**
- 唯一例外：`LipTogether` / `LipTogether_Neg`

    "auGroupNeg": "",

### 5.1.3 完整施加规则（已确定）

```
对每条曲线 C，值 v(t) ∈ [-1, 1]：
  对 controllerConfig[C].attributes 里每个属性 A：
      贡献 = v(t) × A.weight
      施加到 pose = A.pose 的骨骼增量上（按该 pose 的骨/轴/通道）
  A.jawOpen != 0 → 同时更新「张口」通道
  A.blinkScale != 0 → 同时更新「眨眼缩放」通道
```

`pose` 名 = 曲线名（正通道）或 `曲线名_Neg`（负通道），**与 PoseAsset 的 pose 同名**。

`auGroup` 给出该曲线归属的**标准 AU**，供口型合成（音素→口型→AU 容差）与情绪合成（情绪标签→情绪→AU 容差）使用。

## 7. 结论：能做到什么、还差什么

### 7.1 规则本身：已完全确定

```
对每条曲线 C，值 v(t) ∈ [-1, 1]：
  对 controllerConfig[C].attributes 里每个属性 A：
      贡献 = v(t) × A.weight
      施加到 pose = A.pose 的骨骼增量（该 pose 的骨 / 轴 / 通道）
  A.jawOpen ≠ 0   → 同时更新「张口」通道
  A.blinkScale ≠ 0 → 同时更新「眨眼缩放」通道
```

`pose` 名 = 曲线名（正通道）或 `曲线名_Neg`（负通道），与 PoseAsset 的 pose 同名。
`auGroup` 给出该曲线归属的标准 AU，供口型合成与情绪合成使用。

### 7.2 三个角色分别能做到什么

| 角色 | PoseAsset | 曲线→pose 命中 | 能施加什么 |
|---|---|---|---|
| NPC_00401 | **完整**（108/108 非空，13 根骨） | 108 / 108 | **完全可施加**。曲线 → 骨骼增量，规则已被 24 通道独立交叉验证 |
| NPC_06201 | **无** | 113 / 113 | 映射表与 AU 归属已知；**缺每个骨/轴通道的满权重增量** |
| NPC_01101 | 有但几乎空（176 个 pose 里只有 20 个非空，且只涉及 4 根骨） | 175 / 175 | 映射表与 AU 归属已知；**缺 12 根骨的增量**（`Bone053/054/055/063/067/070/079/080/085/086/087/088`），且他的脸本就以变形目标为主 |

### 7.3 唯一剩下的缺口：无 PoseAsset 角色的骨/轴满权重增量

伊里斯那 65 条有效曲线指向 13 根真实存在的脸骨（下巴 / 上下唇 / 嘴角 / 眼皮 / 眉毛 / 舌），蒙皮权重直接绑在真实顶点上 —— 数据是真货，但**「曲线值 1.0 时这根骨该动多少」这个数字不在任何可读资产里**：

- 客户端**没有**通用脸模资产（全量索引检索 `zuiba` / `FaceModel` / `FaceRig` / `AUFace` / `Viseme` 均 0 命中）；
- `/Script/FacialAction` 是**编译态 C++ 模块**（`FacialSubModelConfig`、`FacialWeight` 的类都来自它），其常量读不出；
- `ABP_SKM_NPC_06201_Skin.uasset` 的图是字节码（`ExecuteUbergraph_…` / `AnimGraph` 两个 UFunction，属性数 0），数值常量在字节码里；
- 伊里斯的**所有**原版 clip 都不含脸骨轨道（`CompressedTrackToSkeletonMapTable` 里没有她的 13 根脸骨）—— 没有可对拍的烘焙结果。

### 7.4 一条可行的旁路

`FacialModelConfig.paramsConfig` 暴露了通用脸骨命名与张口通道：

```
AUJawOpen   = "Bone_zuiba_001_z_rotation"
JawOpenValue = 1.0
AUJawOpen2  = "Bone_zuiba_001_x_position"
JawOpenValue2 = -1.0
```

说明原版有一套**标准化脸骨命名**，逐角色配置负责映射到角色自己的骨名。
「标准 AU → 每根骨每个轴的幅度」这套数值在 C++ 模块里，但既然 `auGroup` 已经给出归属，
**同一 AU 在不同角色上的幅度是否相同**是一个可以直接用 `NPC_00401` 验证的问题：

| AU | pose 数 | 平移 (cm) | 旋转 (°) |
|---|---|---|---|
| `10_Upper_Lip_Raiser` | 2 | — | 9.000 / 9.000（一致） |
| `28_Lip_Suck` | 2 | 0.952 / 0.952 | 17.000 / 17.000（一致） |
| `26_Jaw_Drop` | 1 | — | 13.960 |
| `12_Lip_Corner_Puller` | 8 | — | 8.600 … 14.930（不一致） |
| `14_Dimpler` | 4 | — | 10.280 … 12.100（不一致） |

部分 AU 内幅度一致、部分不一致 —— 还不能直接照搬，需要更多样本才能定性。

### 7.5 顺带确认的事实

- **眼睛注视数据在客户端里**：每个 clip 自带 `ec_u_offset_l/r`、`ec_v_offset_l/r`（眼睛材质 UV 偏移），
  伊里斯 94 个 clip 带这个数据，u ∈ [-0.0835, 0.0646]、v ∈ [-0.3215, 0.1108]。
  对应材质函数 `ArtRes/Material/Characters/MatFunc/MF_FacialAnimationUV`。
  **已接入预览（P0，2026-11-08）**，按原始值经 `uGazeOffset` 叠加到 UV；PS 层规则已从 DXBC 确定，未定案的是曲线值层级（见 `docs/05`）。
- **伊里斯不走对话口型管线**：`ArtRes/BP/Lipsync/` 下有 7,360 个口型蓝图，含 `06201` 的 **0** 个。
- **`FacialWeight.uasset`** 是蓝图函数库 `EvalEmotionWeight(Anger, Happy, Sad, Shock, Time, FadeInOutTime)`，
  负责情绪权重淡入淡出；`FacialModelConfig.tagToEmotionTable` 给出中文情绪标签 → 情绪 + 淡入淡出时间。
- **`emotionPADTable`** 用 PAD 三维（Pleasure/Arousal/Dominance）描述情绪权重。

### 8.1 工具改动

`tools/LibScanner/Program.cs` 新增三个能力（均为自建工具，不动轻量包）：

- `--index-name <name>`：索引输出文件名（默认 `library-index.json`）
- `--compact`：紧凑 JSON（1,010,089 行从 ~250 MB 降到 144 MB）
- `--dump`：把匹配到的每个 package 的**属性表**转储成 JSON

`--dump` 的两个关键坑（都踩过）：

1. `System.Text.Json` **只序列化公共属性，不序列化公共字段**，而 `FPropertyTag` 的数据全在公共字段里
   → 必须改用 **Newtonsoft**（CUE4Parse 自带 `MapPropertyConverter` / `FStructFallbackConverter` 等转换器，
   且 Newtonsoft 序列化公共字段）。
2. 直接序列化整个 `UObject` 会把 Owner / Package / Class 图拖进来，
   序列化器报 *"The JSON value of length 759522993 is too large"* → 只序列化 `IPropertyHolder.Properties`。

### 8.2 教训：资产不一定在角色目录下

`FacialConfig/*` 和 `FacialAnimationData/*` 都在 `NRC/Content/NewRoco/DataConfig/` 下，
**不在角色的 `Animation/` 目录里**。此前只按角色目录扫描，所以整批面部配置资产从未进入视野。
一次全量包索引（1,010,089 行）把这个盲区彻底消除。
