# 动画还原

## 动作解码

原版动作是 UE4 `UAnimSequence` + ACL（Animation Compression Library）压缩轨道。解码链：

```
UAnimSequence → CUE4Parse-Conversion.ConvertAnims() → ACL 原生解码 (CUE4Parse-Natives.dll)
    → 逐骨骼的平移/旋转/缩放轨道 → 预览用的 float32 轨道文件
```

`CUE4Parse-Natives.dll` 由轻量包提供（`character/native/`），是 ACL 原生代码的编译产物。

每个 clip 落成一个 `.bin`，头部记录 `magic / frames / bones / duration`，后面是 `frames × bones × 10` 个 float32（每骨骼 3 平移 + 4 四元数 + 3 缩放）。

## 蒙皮校验

解码出来的轨道要能真的驱动网格。校验脚本（`validate_animation_exports.py`）拿网格的**参考蒙皮**（从 `USkeletalMesh` 的 SkinWeight 读出）与解出的轨道重新蒙皮一遍，比对顶点位置：

| 角色 | clips | 骨骼 | 顶点 | 校验 |
|---|---|---|---|---|
| NPC_00401 | 37 | 107 | 13,643 | `passed = true` |
| NPC_01101 | 37 | 104 | 8,522 | `passed = true` |
| NPC_06201 | 96 | 120 | 11,722 | `passed = true` |

伊里斯的具体数值：

```
referenceSkinningErrorCM  1.832560982961695e-05
maxQuaternionNormError    1.1920928955078125e-07
weightSumRange            [1.0, 1.0000001192092896]
```

参考蒙皮误差在 0.000018 cm 量级（远小于任何肉眼可见阈值），四元数范数误差 1.19e-07（float32 精度极限），权重和严格为 1。

**这证明动作是真的在驱动模型**，不是播放一段假动画。

## 导出格式

```
animation/
├── manifest.json        clip 列表、标签、组别（body / face）、来源
├── rig.json             骨骼层级与蒙皮权重
├── skin.bin             蒙皮权重二进制
├── poses.json           附加骨骼姿势（PoseAsset）
├── authored-curves.json 原版面部曲线（来自 TestData 资源）
└── <clip>.bin           每个 clip 的解码轨道
```

### clip 分组

body / face 的划分依据是原版资源的动画语义前缀，不是名字猜的：

- body：`World_`、`Fight_`、`MP01_`、`Ride_`、`Common_`、`Suits` 前缀，外加精确匹配 `Hurt`；
- 其余归 face。

### 标签

`prepare_anim.py` 里维护了一份原版标签表（`World_Crossarms`、`HandOnchest`、`HandOnchin`、`HandReach`、`HandSonhips`、`Fear`、`Greet`、`Think`、`Provoke`、`RolePlay`、`Fight_*`、`Hurt` 等），让下拉框里显示的是「开心动作 · World_Happy_1」而不是裸的资源名。

## 面部曲线

原版表情不是"选一个 pose"那么简单，是**曲线驱动**：

- `authored-curves.json` 记录从原版 `TestData_*.uasset` 导出的曲线；
- 曲线有三种：`命名骨骼曲线`（如 `Bone_Chin_x_position`、`Bone_L_MeiMao01_z_rotation`）、`表情曲线`（`BrowUp` / `BrowDown` / `EyeBlink` / `LipTogether` 及其 `_Neg`）。

伊里斯的 113 条曲线里，**107 条是命名骨骼曲线**，骨骼名确实存在于她的 rig 里（`Bone_Chin`、`Bone_L_MeiMao01`、`Bone_R_MeiMao01` 等），剩下 6 条是表情曲线。

### 路易斯的曲线统计

175 条曲线 / 176 姿势 / 7717 个关键帧 / 80 组符号配对 / 79 组精确镜像；`LipTogether` 非镜像。时间范围 `[0, 8.724998]`。

## 嘴为什么不是骨骼动的

先看 rig 里到底有没有嘴的骨头。

| 角色 | 骨骼 | 与脸相关的骨骼 |
|---|---|---|
| NPC_01101 | 104 | `Bip001-Neck`、`Bip001-Head`、`Bone_Right_Eye_SkinJNT` |
| NPC_06201 | 120 | 上面三根 + `Bone_Chin`、`Bone_Tongue01/02`、`Bone_L/R_ZuiJiao01`（嘴角）、`Bone_L/R_MeiMao01`（眉毛） |

**路易斯没有下巴、没有下颌、没有唇、没有舌。**她的嘴在骨骼上无路可走。

伊里斯虽然多出 `Bone_Chin` 和嘴角骨，但它们只负责很小的位移：`KouXing_Happy` 里 `Bone_Chin` 只转 0.0449，`KouXing_Shock` 转 0.0318；`World_Dialogue_1` 里嘴角骨动 0.644，而 `Bone_Chin` 纹丝不动。

**结论：原版的脸主要由 blend shape（变形目标）驱动，骨骼只是次要修饰。**

## 变形目标驱动表情（已实现）

两块数据在原版里本来就有，之前只是没接上：

| 资源 | 内容 |
|---|---|
| `UMorphTarget` | 每个变形目标对 LOD0 顶点的位移增量 + 法线增量 |
| `UAnimSequence` 的浮点曲线 | 曲线名**就是**变形目标名，曲线值**就是**权重 |

### 两半数据的落盘格式

`NrcChar` 的 `DoPoses` 把 `UMorphTarget` 的 LOD0 delta 解成 `morph-deltas.bin`：

```
uint32 magic (0x4D43524E 'NRCM')
uint32 targetCount
per target:
  int32 vertexCount
  per vertex (28 bytes):
    int32   sourceIndex
    float32 positionDelta[3]
    float32 tangentZDelta[3]
```

位移单位是**米**（原生厘米 × 0.01）。

浮点曲线在 `UAnimSequence` 里是压缩轨道的附属部分：`CompressedCurveNames`（每项一个 `DisplayName`）与 `CompressedCurveData.FloatCurves` **按索引一一对应**，后者每个元素是 `{FloatCurve:{Keys:[{Time,Value,ArriveTangent,LeaveTangent,InterpMode,…}]}}`。

### 按名字配对

`prepare_morph.py` 只保留**名字能命中真实变形目标**的曲线。游戏自己用的工具通道（眼睛材质的 UV 偏移、根运动、缩放等）统计后丢弃，不进包——载荷里不留我们施加不了的曲线。

| 角色 | 变形目标 | 眉 / 眼 / 嘴 | 带曲线的 clip | 命中的曲线 | 关键帧 | 丢弃的工具曲线 |
|---|---|---|---|---|---|---|
| NPC_01101 | 34 | 10 / 12 / 12 | 26 | 125 | 2,175 | `ec_u/v_offset_l/r`、`EC_Eye`、`Move_Velocity`、`x_Scale` 系列 |
| NPC_06201 | 42 | 12 / 16 / 14 | 52 | 535 | 16,121 | `ec_u/v_offset_l/r`、`EC_Eye`、`Move_Velocity`、`Xi_*`、`Jing_*`、`Bei_Mh` |

NPC_00401 **网格里没有 `UMorphTarget`**，也就没有变形目标。加载器按缺失容忍，照常渲染。

单个变形目标影响 39–457（路易斯）/ 42–524（伊里斯）个顶点。

### 「说话」动作本身就带口型

不需要额外的口型片段——原版 clip 自带曲线：

| clip | 原生浮点曲线 | 其中命中变形目标 |
|---|---|---|
| `World_Dialogue_1`（路易斯） | 10 | 6：`Br_Sleep_L/R`、`Et_Sleep_L/R`、`Mh_O_Happy`、`Mh_O_Sad` |
| `World_Dialogue_1`（伊里斯） | 18 | 14：含 `Mh_C_Anger/Happy/Sad`、`Mh_O_Happy/Happy03/Idle/Sad/Shock` |

所以**选中「对话动作」时嘴就会动**，这是原版数据本身的行为，不是我们额外造的。

插值模式统计（命中的曲线）：

| 角色 | RCIM_Cubic | RCIM_Linear | RCIM_Constant |
|---|---|---|---|
| NPC_01101 | 3,226 | 431 | 3 |
| NPC_06201 | 24,399 | 634 | 5 |

**Cubic 占绝大多数**，求值必须走 Hermite 切线插值（用 `ArriveTangent` / `LeaveTangent`），线性近似会明显跑偏。

### 施加顺序

变形目标必须在**蒙皮之前**施加到基座顶点（`skinVertices()` 是从 base 位置取样的），CPU 侧增量更新 position / normal / tangent：

```
base vertex  →  + Σ(weight_i × delta_i)  →  skinning  →  world
```

权重 clamp 到 `[0, 1]`——Cubic 切线会过冲，原版 blend weight 同样不会超过 1。

### 浏览器验证

同一帧 A/B（伊里斯 `World_Dialogue_1`，时间轴 0.567 ≈ t = 2.27 s）：

| | 嘴 | 眉 |
|---|---|---|
| 变形目标开 | 张开（能看到口腔） | 随表情曲线变化 |
| 变形目标关 | 闭合成一条细线 | 回到中性 |

该帧上多个嘴部目标同时非零（`Mh_O_Sad`=0.92、`Mh_C_Happy`=0.63、`Mh_O_Shock`=0.10），叠加出来的就是那个张开的嘴。控制台 0 error / 0 warning。

## 没有 PoseAsset 的角色

`PA_<NPC>_Skin.uasset` 可能是 PhysicsAsset 而不是 PoseAsset。`NrcChar` 里对 `PA_` 前缀做了过滤，并在诊断输出里打印 `POSE CANDIDATES` 与每个包的导出类型，**这种情况要如实记录，而不是借用别的角色的姿势**。

伊里斯就属于这种：姿势集导出为空，113 条原版曲线原样导出留档。

`prepare_anim_noposeasset.py` 是为这类角色准备的——它解出原版曲线、写出**空的** `poses.json`，并在 manifest 里注明 `facialCurves` 的来源说明。

同样地，`prepare_anim_nopose.py` 会写出**空的** `authored-curves.json`（624 bytes，内容明确记录 "Empty by source, not by omission"），避免预览因为缺文件直接报 `Missing bundled asset`。

## 预览里能做什么

- 原版 clip 直接播放（身体动作 + 面部动作分开选择）；
- 附加骨骼姿势按原版增量叠加，权重可调；
- **原版变形目标表情**（眉 / 眼睑 / 嘴）由 clip 自带的曲线实时驱动，可一键开关做 A/B 对照；
- 表情曲线样例仅在角色确实拥有对应 PoseAsset 时才出现在选项里。

**表情曲线的混合语义已经查清**（映射表在 `NewRoco/DataConfig/FacialConfig/`，规则见 [06-面部混合语义.md](06-面部混合语义.md)）：

```
曲线名 C → FacialSubModelConfig_NPC_<npc>.controllerConfig[C]
        = { auGroup, auGroupNeg, attributes:[{pose, weight, jawOpen, blinkScale}] }

对每个属性 A：贡献 = v(t) × A.weight，施加到 pose = A.pose 的骨骼增量
```

`pose` 名与 PoseAsset 的 pose **同名**（正通道用曲线名，负通道用 `曲线名_Neg`），
`auGroup` 给出该曲线归属的标准表情动作（`26_Jaw_Drop`、`12_Lip_Corner_Puller` 等）。

还差的部分见 [05-未完成与限制.md](05-未完成与限制.md)。
